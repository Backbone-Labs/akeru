# Hypersomnia feasibility

The pinned upstream source is `TeamHypersomnia/Hypersomnia` at
`e4dd2c8f87358cb83cfdef5b352093379907147c`. This package is a source assessment,
not a playable port. It exports no title manifest, catalog factory, or server.
No Hypersomnia server or public match was started.

Run `HYPERSOMNIA_SOURCE=/path/to/checkout node packages/hypersomnia/feasibility.mjs`
to verify the inspected files against the root inventory and write an ignored
`dist/hypersomnia-feasibility/report.json`. Source changes and a wrong revision
are rejected. The existing rights audit remains pending.

## Findings at the pinned revision

- `CMakeLists.txt:278` forces web networking and WebRTC on even if the caller
  specifies `BUILD_NETWORKING=OFF`. An offline fork needs an explicit patch and
  a runtime network assertion, not just a build flag.
- `src/application/setups/test_scene_setup.cpp:52` loads the built-in tutorial;
  the same setup supports the shooting range. This is the strongest offline
  candidate. A functioning offline bot match has not been established.
- `cmake/web/assets/common.js` initializes `/user` through IDBFS, sends OAuth
  data into the engine, fetches remote avatars and geolocation, and contains
  optional CrazyGames hooks. This bootstrap cannot be adopted wholesale by a
  game restricted to host-owned saves and account interfaces.
- The source inventory contains eleven unexpanded gitlinks, including the
  introspector generator, ImGui, Yojimbo and datachannel-wasm. Each selected
  dependency needs its pinned content and notices inventoried. No parent AGPL
  grant is assumed to cover them.
- The web configuration requires native introspector and version generators,
  a content cache generated by running the game, and currently reserves
  1200 MB of initial WASM memory plus a 4 MB stack. No mobile memory or input
  conformance result exists.

The next implementation should select tutorial/range, remove online bootstrap
and networking code, build the selected dependencies from source, replace
`/user` persistence, map controller/touch controls, and run isolated browser
checks before a playable card is introduced. A multiplayer variant additionally
needs an explicit hosted-service and moderation decision. None of these gates
is satisfied by the existence of the upstream browser demo.

No upstream files, assets or binaries are committed here. This document is not
publication or rights approval.
